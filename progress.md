### 2026-10-12: Fluxo de exclusão de conta (anonimização + limpeza real de S3/Stripe), resolvendo o HIGH "Fluxo de exclusão de conta incompleto" (RNF-DATA-05 / RF-AUTH-05)
- **Commit(s):** nenhum ainda — alterações deixadas no working directory para revisão do usuário
- **Contexto:** o webhook `user.deleted` do Clerk só fazia `db.user.delete({ where: { id } })` — com `onDelete: Cascade` no schema, isso já apagava `UploadedFile`/`Clip`/`CreditTransaction`/`Subscription` em cascata, mas **não apagava nada do S3** (vídeos/clipes ficavam órfãos pra sempre) e **não cancelava a assinatura na Stripe** (continuava cobrando). ### 2026-10-12: Rate limiting com estado compartilhado (Upstash Redis), resolvendo o HIGH "in-memory não funciona em serverless" (RNF-RL-06)
- **Commit(s):** nenhum ainda — alterações deixadas no working directory para revisão do usuário
- **Contexto:** item HIGH do checklist ("Rate limiting in-memory não funciona em serverless" — `InMemorySlidingWindowRateLimiter` reinicia a cada cold start, proteção inefetiva em múltiplas instâncias). Decisão do usuário: Upstash Redis (REST, sem conexão persistente — padrão de mercado pra serverless/edge).
- **O que foi feito:** nova classe `src/infrastructure/rate-limiting/upstash-redis-rate-limiter.ts::UpstashRedisRateLimiter`, implementando a mesma porta `IRateLimiter` (`consume(key): Promise<boolean>`) — nenhum call site precisou mudar. **Algoritmo escolhido: fixed window counter** (`INCR` + `PEXPIRE key windowMs NX` num único pipeline), não sliding window de sorted set (`ZADD`+`ZREMRANGEBYSCORE`+`ZCARD`). Motivo: só 2 comandos por `consume()` (relevante porque a Upstash REST API cobra por requisição) e atomicidade sem race read-then-write (`PEXPIRE ... NX` só define TTL na primeira vez que a chave é criada na janela, não-op nas seguintes — sem gap entre "ler contador" e "setar expiração"). Trade-off aceito e documentado no comentário da classe: um fixed window pode permitir até ~2x o limite numa borda de janela; julgado aceitável para os limites atuais (5-20 req/60s, throttling de abuso, não SLA rígido).
- **Fallback (decisão explícita):** `src/infrastructure/factories/rate-limiter-factory.ts::createRateLimiter` só usa `UpstashRedisRateLimiter` quando `UPSTASH_REDIS_REST_URL` **e** `UPSTASH_REDIS_REST_TOKEN` estão configuradas; sem qualquer uma delas, cai para `InMemorySlidingWindowRateLimiter` (comportamento de hoje), sem lançar erro — é o esperado em dev/CI, que não têm conta Upstash. As 2 env vars novas são opcionais em `src/env.js` (`z.string().url().optional()` / `z.string().optional()`, mesmo padrão de outras opcionais no arquivo) e documentadas em `.env.example`.
- **TDD (RED→GREEN):** `tests/unit/infrastructure/rate-limiting/upstash-redis-rate-limiter.test.ts` (5 casos, client Upstash mockado via uma fake class que modela o próprio TTL/NX do Redis com um clock controlado pelo teste — não `vi.useFakeTimers`, já que o código de produção não lê `Date.now()` diretamente): limite respeitado dentro da janela, bloqueio acima do limite, reset após expirar o TTL, chaves independentes, e uma verificação indireta de atomicidade (os comandos exatos — `incr`/`pexpire` com `"NX"` — enviados ao client, não só o resultado final). `tests/unit/infrastructure/factories/rate-limiter.factory.test.ts` (4 casos, novo arquivo — não existia teste de factory antes): sem env vars → in-memory; só uma das duas presente → ainda in-memory; ambas presentes → Upstash; singleton estável entre chamadas repetidas (os 5 `make*RateLimiter()` são módulo-level, preservados sem mudança de assinatura). RED confirmado no teste de factory antes de alterar `rate-limiter-factory.ts` (3/4 passavam, o cenário "ambas presentes" falhava como esperado); GREEN depois.
- **Verificação (execução real em 2026-10-12):** `npm run check` 0 erros/0 warnings (1 erro de lint intermediário — `no-unnecessary-type-assertion` num cast redundante — corrigido antes do commit final). `npm run test` 882 passed/8 skipped (baseline 873 + 9 novos, sem regressão). `npm run test:integration` 130 passed/17 failed (mesma contagem exata da baseline — as 17 falhas são `ECONNREFUSED 127.0.0.1:3000`, dev server não estava de pé nesta sessão, pré-existentes e não relacionadas a esta mudança). Nenhum serviço em `:3000`/`:8000`/`:8288` estava de pé no início da sessão; nenhum foi iniciado/parado.

Falta o usuário criar uma conta Upstash, uma database Redis, colocar `UPSTASH_REDIS_REST_URL`/`UPSTASH_REDIS_REST_TOKEN` reais no `.env` e confirmar manualmente (idealmente simulando 2+ instâncias/processos) que o limite passa a ser de fato global antes do go-live.

## Como Adicionar uma Nova Entrada ao Histórico

Ao finalizar um marco/feature relevante, adicione uma entrada no topo do **Histórico** com este formato:

```
### YYYY-MM-DD: Título do Marco (máx. 60 caracteres)
- **Commit(s):** `hash1`, `hash2` (ou range se for muitos)
- **O que foi feito:**
  - Ponto 1 com detalhes técnicos relevantes
  - Ponto 2
- **Por quê:** Breve explicação do impacto ou razão (para quem lê depois, entender o contexto)
```

**Notas:**
- Data: aproximada (use a data do commit mais significativo ou da conclusão)
- Commits: use apenas hashes curtos (7 caracteres) dos 1-3 commits mais relevantes
- "O que foi feito": lista técnica de mudanças reais (verificar `git log` e código)
- "Por quê": foque no **por quê** (impacto no usuário, conformidade, arquitetura) não no **como** (detalhes de implementação)
- Não invente marcos — baseie-se sempre em commits reais ou arquivos criados no projeto
- Mantenha conciso: máx. 5-7 bullets por entrada; detalhe vai para a documentação em `docs/` quando necessário
